### Amazon DynamoDB (+ DynamoDB Local) ◐
- **Used for:** Users, Lines, Grants, Watches, Audit, BindTokens (prompt 05, 2026-10-06), via the boto3 low-level client from `packages/tower-consent`. Tested against DynamoDB Local (`amazon/dynamodb-local:latest`, started by testcontainers) and moto, same suite on both: 118 tests, all green on both backends.
- **Worked well:** conditional writes carry the whole consent model — `attribute_not_exists(line_id)` makes `bind_line` idempotent and refuses a number owned by someone else; `attribute_not_exists(line_id) OR attribute_exists(revoked_at)` allows re-granting after a revoke; `attribute_not_exists(#ls) OR #ls.#at < :at` (a nested map path) makes `Watches.last_state` updates last-writer-by-timestamp. A conditional `DeleteItem` (`user_id = :u AND expires_at > :now`) is a single-use token in one request. botocore's `before-call.dynamodb` event let a test assert `resolve` makes exactly `["Query"]` — the "one read on the hot path" claim is a test, not a comment. DynamoDB Local was up in ~7.7 s including the container start; `UpdateTimeToLive` is accepted.
- **Needs work:** `Limit` on a `Query` with a `FilterExpression` applies *before* the filter, so "find the grant with this alias, Limit 1" silently returns nothing when the first item doesn't match — `resolve` drops `Limit` on the alias branch (one request still; a grantee has a handful of grants). TTL deletion is lazy (up to days on AWS; never on Local), so expiry must be re-checked on every read — easy to miss if you trust the TTL. No cross-item uniqueness: "one unrevoked alias per grantee" needs a query-then-put (or a sentinel item + transaction); we accepted the query-then-put race at human write speed. `TypeDeserializer` returns `Decimal` for every number, which pydantic and `json` both dislike; we wrote a 10-line `_plain()`. ISO timestamps only sort correctly if fixed-width — we store `%Y-%m-%dT%H:%M:%S.%fZ` because pydantic's default JSON drops zero microseconds (`...:00Z` sorts after `...:00.5Z`).
- **Onboarding, zero to hello world:** DynamoDB Local in Docker plus `endpoint_url=` was working in minutes; the table definitions as data (`tables.py` → `CreateTable` kwargs and Terraform JSON) took longer than the code that uses them.
- **Build with it again?** Yes — single-digit-ms key reads and conditional writes are exactly what a consent store with "revocation must never lie" needs; we'd write the fixed-width timestamp and Decimal handling on day one next time.
- **Audit log (prompt 07, 2026-10-06):** `TransactWriteItems` with two `Put`s on the same partition (the row, conditional on `attribute_not_exists(ts_seq)`, and a per-line head item, conditional on `last_ts_seq = :prev`) makes the hash chain fork-proof under concurrent writers — a plain conditional `PutItem` cannot express "no newer row exists". A lost race surfaces as `TransactionCanceledException` on both moto and DynamoDB Local; one re-read and retry covers it (tested by interleaving a second writer). **Needs work:** which condition failed is only in `CancellationReasons`; the exception message alone doesn't say. Package suite: 120 tests (40 store cases on each of moto and Local, plus unit), all green.
- **Local compose (prompt 12, 2026-10-06):** **DynamoDB Local 2.x rejects an access key id that is not alphanumeric.** `AWS_ACCESS_KEY_ID=dynamodb-local` gave `UnrecognizedClientException: The Access Key ID or security token is invalid` on `ListTables`, so the Alerts container exited at start-up. `dynamodblocal` works. The usage notes for recent DynamoDB Local versions do state the letters-and-digits rule, but the error message never mentions it. Our test suites happened to use `testing`, which passes the rule. The `curl` in the image serves as the healthcheck: any HTTP answer to a bare GET means the JVM is up.
- **Binding page (prompt 09, 2026-10-06):** **DynamoDB Local runs a TTL sweeper on wall-clock time.** Tests with a fixed clock (`2026-10-06 14:30Z`) wrote `BindTokens` with `expires_at` = clock + 10 min. Once the real time passed that, Local deleted the "fresh" tokens partway through a test: 8 of 46 tests failed on `[local]` with a 404 on the second read, while moto, which has no sweeper, passed all of them. The fix was to start the test clock at the real minute. The TTL docs say deletion happens "within a few days" on AWS, and nothing says Local sweeps within seconds, so a fixed past test clock is a trap on Local only. The same fixed-date pattern is still in the 05/07 package conftests (logged).
- **Watch settings (D8/D9, 2026-10-09):** one `UpdateItem` with `SET #p = :p, #esc = :esc, #e = if_not_exists(#e, :off), #s = if_not_exists(#s, :none)` creates the line-holder's Watch *off* on the first save and keeps whatever voice set on later saves, without a read — and never touches `last_state`. **Needs work:** **botocore logs a 10-digit `x-amz-crc32` response header at DEBUG.** A privacy test that captures every log record at DEBUG (no number-shaped run in any line) failed on botocore's own `Response headers: {... 'x-amz-crc32': '2045755197'}`, not on our code. botocore's DEBUG output is a wire dump (request bodies, ciphertext, headers), so the binding page now pins `botocore`/`boto3`/`urllib3` to WARNING in its composition root whatever `LOG_LEVEL` says. Nothing in the SDK docs warns that turning on DEBUG puts payloads in your logs. The same 10-digit-run trap hit the audit reconcile test the other way round: a wall-clock `NOW` (required by DynamoDB Local's TTL sweeper) next to hard-coded trace dates drifted out of the 24 h window three days later; the dates are now relative to `NOW`.
- **Alerts on the compose stack (2026-10-11, build-log/22-ops.md R1):** the TTL sweeper bit production code, not just tests. Alerts computed `AlertsState.expires_at` from the mock carrier's scenario clock (2026-10-05, six days behind the real date), so a parked escalation's TTL was already past by the wall clock; DynamoDB Local 2.5.2 deleted the row about 0.8 s after the write, with no log line anywhere, and the 15-minute escalation found nothing in about 6 of 10 e2e runs. It looked like a race. We found it only by polling a filtered `Scan` every 100 ms beside the mock's clock. Fix: every TTL is now `wall + horizon` from an injected wall clock, and every window compares against the service clock (06 §7 "Clocks"). **Needs work:** an expired-item deletion that is silent and near-instant on Local but "within a few days" on AWS means Local is *stricter* than the service in a way the docs don't mention; a sweeper log line (or a `-disableTtlSweeper` flag) would have made the cause visible at once. Note that the earlier bullet's "never on Local" is wrong for Local 2.x.

## Other tools and SDKs

### CAMARA OpenAPI specifications (GSMA Open Gateway) ◐
- **Used for:** the mock carrier's routes, request validation, error codes and conformance suite (prompt 04, 2026-10-06). Six files vendored byte-for-byte from the **Fall25** meta-release: SimSwap `r3.3` (sim-swap 2.1.0, sim-swap-subscriptions 0.3.0), CallForwardingSignal `r3.3` (0.4.0), NumberVerification `r3.2` (2.1.0), DeviceReachabilityStatus `r1.2` (1.1.0, subscriptions 0.8.0) — URLs, tag commits and SHA-256s in `specs/camara/README.md`.
- **Worked well:** clean OpenAPI 3.0.3; every operation has an `operationId`; every error response is an `allOf` with a per-operation `code` enum, so "the mock only emits codes the spec allows for that operation" is checked by schemathesis rather than by us. Raw files at `raw.githubusercontent.com/camaraproject/<Repo>/<tag>/code/API_definitions/` — no build step.
- **Needs work:** (1) Finding "the latest meta-release" means reading four repos' tags and CHANGELOGs: each repo numbers its own cycle (`r3.3` vs `r3.2` vs `r1.2` are all Fall25), DeviceReachabilityStatus's CHANGELOG never says "Fall25", and on 2026-10-06 the newest tags (`r4.1`, `r2.1`) were all `-rc` — ~20 min. (2) Rules that decide the status code live in prose, not schema: two-legged vs three-legged identifier handling (422 `MISSING_IDENTIFIER` / `UNNECESSARY_IDENTIFIER`), so a schema-valid body is legitimately refused. (3) The subscription `Protocol` enum lists `MQTT3/MQTT5/AMQP/NATS/KAFKA`, yet `Generic400` carries `INVALID_PROTOCOL` "Only HTTP is supported" — schema-valid, spec-refused. (4) Subscription create declares no 404, so an unknown number has to be 422 `SERVICE_NOT_APPLICABLE` there but 404 `IDENTIFIER_NOT_FOUND` on `check`. (5) `retrieveCallForwarding` returns a bare JSON array, not an object. (6) Commonalities 0.6 removed `DEVICE_NOT_FOUND` and `UNIDENTIFIABLE_DEVICE`; Number Verification's "not on mobile data" is now 403 `NUMBER_VERIFICATION.USER_NOT_AUTHENTICATED_BY_MOBILE_NETWORK` — our docs, written against the older names, changed (08, 05 §5). (7) Unquoted `example: 2023-07-03T14:27:08.312+02:00` values load as YAML timestamps, which breaks JSON serving (`TypeError: Object of type datetime is not JSON serializable` from Starlette's `JSONResponse`); we load with a timestamp-free SafeLoader.
- **Alerts webhooks (prompt 10, 2026-10-06):** the subscription APIs define the notification as a `CloudEvent` schema plus a `type` → event-schema discriminator mapping inside the OpenAPI document, not as a standalone JSON Schema; we extract it (`services/alerts/scripts/vendor_schemas.py`, `--check` in the tests) so the receiver validates without the full specs. The Fall25 reachability-subscriptions API takes one event type per subscription, so a `transplant` watch needs three reachability subscriptions plus the SIM-swap one. `time` is `format: date-time`, which `jsonschema` only enforces with optional extras installed — we check RFC 3339 ourselves.
- **Onboarding, zero to hello world:** ~20 min to settle the release set and URLs; first conformant `check` endpoint ~1 h later.
- **Build with it again?** Yes — a judge can diff our served `/openapi.json` against the public files, and a sandbox is a base-URL swap.

### MCP Python SDK / FastMCP · MCP Inspector ◐
- **Used for (prompt 06, 2026-10-06):** `fastmcp` 4.0.11 (on `mcp` 2.3.0) for the carrier client's Gateway path. `fastmcp.Client` is the MCP client inside `GatewayClient`. `FastMCP` with hand-built `Tool` subclasses (explicit JSON-Schema `parameters` taken from the CAMARA request schemas) is the in-process fake Gateway. They connect with `Client(server)`, in memory, with no ports.
- **Worked well:**
  - The in-memory transport makes an MCP round trip a plain `await`: 162 fixture cases through Gateway → mock run in the same pytest process as the direct path.
  - `call_tool(..., raise_on_error=False, meta={...})` returns `is_error` plus content blocks instead of raising, so carrier errors keep their status and code.
  - The server reads `meta` via `get_context().request_context.meta`.
  - After warm-up a per-call `async with Client(server)` costs about 3 ms.
- **Needs work:**
  - The `mcp` SDK 2.x removed `mcp.server.fastmcp`. Importing it now raises `ModuleNotFoundError` with a pointer to "MCPServer". Our conventions said "FastMCP", which led us to the standalone `fastmcp` package. That package pulls in about 30 dependencies (keyring, rich, cyclopts, websockets, beartype via py-key-value) and `httpx2` alongside `httpx`.
