# 01 — Alexa+ Surface

**Role:** the MCP client. Turns speech into a tool call, and a structured result into speech.
**Runs on:** Alexa+ (US), or the Alexa+ MCP Toolkit **web simulator** for the demo from Canada.
**Owns:** nothing. Tower holds no Alexa-specific state beyond the account-link id.

---

## 1. What it does and does not do

| Does | Does not |
|---|---|
| Decide, from the user's words and the tool descriptions, which Tower tool to call | Read SMS, notifications, or anything on the phone |
| Pass the account-linked user id with every call | Speak unprompted — MCP add-ons are request/response only |
| Phrase Tower's structured result into a sentence | Make or gate decisions; it is not on the policy path |
| Ask a clarifying question when a tool argument is missing ("which line — yours or Mom's?") | Hold consent, bindings or alert state |

The second row of "does not" is load-bearing: every proactive behaviour in the system goes through SMS/push from the Alerts service (component 06), never through Alexa.

## 2. Tool descriptions as the interface

Because Alexa+'s model chooses tools from their descriptions, the descriptions *are* the voice UX. They are written for a model deciding under a latency budget, not for a human reading docs:

```yaml
line_is_ok:
  description: >
    Check whether the user's phone line, or a line they have been granted
    access to, has been SIM-swapped recently or has call forwarding set.
    Use when the user asks if their line/phone/number is OK, safe, swapped,
    hijacked, forwarded, or why their phone lost signal. Returns facts only.
  args:
    line: "self" | alias (e.g. "mom"); default "self"

is_reachable:
  description: >
    Whether a phone line is currently attached to the mobile network.
    Use when the user asks if a phone is on, reachable, or has signal.
    Does not return location.
  args:
    line: "self" | alias

watch_line:
  description: >
    Turn alerts on or off for a line the user holds or has been granted.
    When on, the user is texted if the line is SIM-swapped or forwarded.
  args:
    line: "self" | alias
    enable: boolean | null   # null = status: watching?, who has grants, recent checks
```

Three descriptions, each naming the *user phrasings* that should trigger it. Nothing else is exposed; a tool that isn't there can't be called.

## 3. Result shaping for voice

Tower returns JSON; Alexa+ speaks it. To make that reliable without a second model:

- Every result carries a `summary` string Alexa+ may read verbatim, and `facts` it may reason over. Example:
  ```json
  {"summary": "Your SIM was moved to another device at 2:14 today. If that wasn't you, call your carrier now.",
   "facts": {"sim_swapped_recently": true, "swapped_at": "2026-10-05T14:14:00Z",
             "call_forwarding": "none", "line": "self"},
   "next_step": {"kind": "call_carrier", "carrier_support_number": "+1 ..."},
   "reason_codes": ["SIM_SWAPPED_RECENT"]}
  ```
- `summary` is generated by **templates in Tower**, keyed on reason codes — not by a model. The same inputs always produce the same sentence, which is what makes the demo repeatable.
- Numbers in `summary` are spoken-friendly ("2:14 today", not an ISO timestamp).

## 4. Account linking and identity

Alexa+ passes an account-linked user identity to the MCP server. Tower maps it to a `user_id` in the consent store. **Line binding is not account linking**: linking tells Tower who is speaking; binding (component 04) proves which phone number is theirs. Both are required before `line_is_ok("self")` returns anything.

**Assumption coded in Tower (prompts 08, 15; spike A not yet run):** account linking is OAuth 2.0 against an identity provider we run (the runbook uses Amazon Cognito; `../alexa/registration.md`), and the identity arrives as that provider's access token, `Authorization: Bearer <JWT>`, verified against `TOWER_JWKS_URL` (`exp`, `sub` required; issuer when configured; `aud` against `TOWER_JWT_AUDIENCE` and `client_id` against `TOWER_JWT_CLIENT_IDS` when configured — Cognito access tokens have `client_id` and no `aud`, as AgentCore Runtime's `allowedClients` reflects); `user_id` = `sub`. One linked Amazon account (Asish's) is enough for the demo: Mom is a consent-store user who granted `watch`, not an Alexa user. A subject that is not an opaque id (outside `[A-Za-z0-9._:@+-]{1,128}` or containing a run of 10+ digits) is mapped to `u_` + 40 letters of its SHA-256, so the audit log never stores something shaped like a phone number. Local mode only: static bearer + `X-Tower-User`. Replace when spike A shows the real shape (`services/tower-mcp/src/tower_mcp/auth.py`).

## 5. Constraints to design around

| Constraint | Source | Consequence |
|---|---|---|
| MCP Toolkit available in the US; web simulator for testing | toolkit docs | Demo runs in the simulator from Ottawa; the ask on the closing slide |
| Request/response only | toolkit docs | Proactive path is SMS (06) |
| Tight response-time expectation for tool calls (the review cites ~500 ms) | review, lifecycle docs | Hot path has no model and one DynamoDB read; measured in week one |
| Tool choice is the model's | MCP | Descriptions name user phrasings; the reference client (09) tests them |
